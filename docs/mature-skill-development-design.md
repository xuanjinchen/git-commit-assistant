# 成熟 Skill 独立开发设计

## 状态

- 日期：2026-08-19
- 状态：已确认
- 适用对象：负责从零设计、实现、验证和交付 Agent Skill 的开发 Agent

## 目标

形成一套与具体业务和 Agent 平台解耦的分层方法，使开发 Agent 在获得初始 Skill 目标后，可以独立完成需求固化、Skill 设计、最小实现、确定性验证、行为评测、按需工程化、安全检查和发布准备。

最终计划必须既能指导简单的单文件 Skill，也能指导包含脚本、领域资料、安装器、多 Agent 适配和公开发布流程的工程化 Skill。工程能力按证据启用，不要求每个 Skill 复制未被当前目标证明必要的结构。

## 非目标

- 不实现一个通用 Skill 生成器或脚手架 CLI。
- 不规定所有 Skill 必须使用 Node.js、独立安装器或 GitHub Release。
- 不把某个 Agent 的私有约定描述为跨平台标准。
- 不以增加文件、适配器或测试数量代替真实行为质量。
- 不允许 Agent 在未验证时宣称兼容某个平台或 Agent。

## 设计原则

### 用户目标优先

Skill 只解决已确认的核心问题。每项脚本、资源、适配器和发布能力都必须能追溯到用户场景或验收要求，不能因为参考项目具备某项能力就默认加入。

最新用户要求始终优先于旧 Brief、旧计划和默认设计。发生冲突时，先保留冲突记录并更新当前需求版本，再撤销或调整已失效结论；只有付费、凭据、破坏性操作和公开发布等授权边界需要再次确认。

### 核心与增强分离

所有 Skill 执行核心轨道；只有满足明确条件时才启用增强轨道。核心轨道保证 Skill 可发现、可理解、可评测，增强轨道解决重复执行、复杂资料、隐式触发、跨 Agent 安装或公开维护等额外问题。

### 渐进披露

元数据只承担发现与触发，`SKILL.md` 承担核心决策和工作流，`references/`、`scripts/`、`assets/` 只在相关任务中加载或执行。不得把所有领域知识、平台差异和示例堆入主提示。

### 证据驱动

确定性契约、行为评测、真实 Agent 运行和人工判断分层验证。昂贵或依赖外部服务的评测不进入默认 CI，但正式兼容声明必须有真实运行证据。

### 保守写入

任何会修改用户配置、全局规则或已有文件的增强能力，都必须具备所有权识别、预检、原子提交、失败回滚、幂等升级、保守卸载和只读诊断。

### Token 受控

评估触发元数据、主 Skill、按需资源和输出协议四层预算。优先删除重复规则、无效示例和可由脚本确定完成的推理，不能通过删减关键约束换取表面上的 Token 降低。

## 总体架构

开发流程采用十个阶段和两类轨道。每个阶段必须定义输入、动作、产物、验证、通过条件、失败恢复和继续条件。

1. 输入契约：将初始请求整理为版本化 Skill Brief。
2. 需求与风险：识别用户、场景、边界、权限、数据和依赖。
3. Skill 设计：确定触发语义、工作流、输出、失败策略和资源边界。
4. 最小实现：先交付可发现、可加载、可执行的核心 Skill。
5. 确定性验证：验证结构、语法、引用、契约和边界。
6. 行为评测：比较有 Skill 与基线行为，检查质量与触发准确性。
7. 按需工程化：实现已被证据证明必要的增强轨道。
8. 安全与开源：检查敏感信息、权限、依赖、许可证和仓库治理。
9. 发布与维护：准备版本、升级、回滚、变更日志和发布资产。
10. 最终验收：执行需求追踪、全量验证和独立复核。

## 核心轨道

每个新 Skill 至少交付以下能力：

- 有效的 `SKILL.md`，包含准确的 frontmatter、触发描述、核心工作流、边界和输出要求。
- 版本化 Skill Brief，记录目标、非目标、用户场景、默认选择和验收标准。
- 决策日志，记录重要取舍、需求覆盖和被废弃的旧结论。
- 行为评测集，覆盖正向触发、隐式触发、负向触发、边界、冲突和失败场景。
- 面向使用者的安装、使用、限制、验证和卸载或移除说明。
- 与仓库技术栈一致的统一验证入口。

核心轨道不强制独立运行时依赖。单纯的提示型 Skill 可以只包含 `SKILL.md`、必要资源、评测和文档。

## 增强轨道

### 确定性脚本

当多个评测重复生成相同辅助逻辑，或任务存在可机械验证的转换时，启用 `scripts/`。脚本必须拥有明确输入输出、稳定退出码、错误信息和隔离测试，不能替代仍需 Agent 判断的领域决策。

### 领域资料与资产

当主 Skill 接近上下文预算、支持多个领域变体或依赖大段规范时，启用 `references/`。当输出依赖模板、图标或固定素材时，启用 `assets/`。主 Skill 必须说明何时读取哪个资源，避免全量加载。

### 隐式自动触发

当仅靠 Skill description 无法保证某类任务自动进入工作流时，可以增加用户级或项目级规则模板。规则层只负责要求加载 Skill 和建立不可缺失的流程门，详细业务逻辑仍保留在 `SKILL.md`，避免形成多份真相来源。

### 多 Agent 正式适配

只有目标用户明确需要多个 Agent，且每个 Agent 的安装位置、规则文件、调用语法和 headless 运行方式都已确认时，才增加适配器。适配器共享同一业务规则，只封装平台差异。未完成真实 CLI 评测的平台只能标记为通用模板或实验性支持。

### 安装与配置管理

当交付需要写入多个用户目录、全局规则或共享 Skill 副本时，才启用安装器。跨平台项目优先选择团队可维护且目标环境普遍具备的运行时；若选择 Node.js，使用标准库和统一 CLI 管理安装、升级、诊断和卸载。

安装器必须先完成所有目标预检，再产生文件系统副作用。它只能删除自己能够证明拥有的文件或托管区块，不能接管其他工具安装的副本。

### 开源发布

当 Skill 需要公开分发和版本维护时，启用 CI、安全扫描、贡献规范、语义化版本、变更日志和不可变 Tag。发布包采用明确白名单，并验证包内容、校验文件和从固定 Tag 安装的结果。

## 自主执行模型

开发 Agent 默认连续执行全部适用阶段，不为低风险实现细节逐项请求批准。以下情况必须暂停：

- 新要求与核心目标、非目标或验收标准冲突。
- 操作涉及凭据、付费服务、公开发布、数据删除、历史重写或其他不可逆影响。
- 关键外部依赖无法获得，且替代方案会改变正式能力声明。
- 存在多个影响用户行为或兼容性的合理解释，无法从项目证据中确定优先级。

普通技术选择由 Agent 根据项目规范、维护成本和验证证据决定，并写入决策日志。

## 需求变更协议

需求优先级固定为：最新明确用户指令、当前 Skill Brief、项目就近规范、计划默认值。

收到变更后，Agent 必须：

1. 暂停受影响工作，不继续传播旧假设。
2. 更新 Skill Brief 的需求版本和决策日志。
3. 标识被覆盖、保留和新增的要求。
4. 分析设计、实现、测试、文档、兼容性和发布影响。
5. 回退到最早受影响阶段，废弃失效产物或测试预期。
6. 重跑受影响质量门和最终全量门。

低风险且兼容的变更可自动合并；改变核心行为或正式支持范围的变更只提出一个阻塞问题；安全或不可逆操作始终等待授权。

## 产物模型

计划应区分仓库交付物和开发工作区记录。仓库交付物进入版本控制；临时运行记录、模型输出和评测工作区按仓库策略忽略。

建议的核心交付物包括：

- `SKILL.md`
- `README.md`
- `evals/evals.json`
- 项目选定位置下的 Skill Brief 与决策日志
- 统一验证脚本或命令

可选交付物包括：

- `references/`
- `scripts/`
- `assets/`
- Agent 元数据和适配器
- 安装、诊断、卸载和状态管理模块
- CI、安全、发布和开源治理文件

计划不得固定不存在于目标仓库的目录。执行 Agent 必须先检查项目结构，再锁定实际路径和命名。

## 证据引用契约

Evidence Contract v1 只接受稳定 ID 和仓库相对引用，不从任意 prose 推断能力。每个契约字段使用规定的一种引用：

- `artifact:path#sha256` 表示 `artifact:<path>#sha256:<64 位小写十六进制摘要>`，固定产物字节。
- `path:` 表示 `path:<path>`，定位一个实现文件。
- `eval:` 表示 `eval:<evaluation-id>[,<evaluation-id>...]`，引用评测集中一个或多个唯一案例。

enabled 轨道、Prompt 预算、评测结果和能力声明使用 `artifact:`；交付实现使用 `path:`；交付验证使用 `eval:EVAL-001,EVAL-002`。disabled 轨道写明理由，blocked 轨道使用 `required:<work>;impact:<delivery-impact>` 并提供解除条件。

确定性 Gate 验证引用结构、状态和闭合关系，但不调用 Agent，不证明模型真实运行，也不证明文本证据真实。正式行为与兼容声明必须另有可复现的真实运行记录和人工判断。

## 质量门

### 需求门

目标、非目标、触发、输入、输出、风险、默认值和验收标准完整且无冲突。

### 结构门

frontmatter 可解析，名称和目录一致，资源引用存在，主 Skill 保持聚焦，安装发现机制有效。

### 触发门

显式和隐式正向场景能触发；相邻但不应触发的场景保持不触发；否定表达、作用域和冲突优先级有测试证据。

### 行为门

输出满足领域正确性、约束、边界、失败处理和用户指定格式。有 Skill 结果相对无 Skill 或旧版本基线产生可解释的收益。

### 回归门

确定性测试、已有行为、资源引用、安装生命周期和适配器契约均通过。修复后的测试必须先证明能够捕获原问题。

### 效率门

元数据、主 Skill、按需资源和输出协议均有预算；重复内容和不区分结果的评测被删除；昂贵评测只有显式入口。

### 安全门

不存在真实凭据、私人路径、私人邮箱、危险默认操作、越权写入、意外打包文件或未固定的高风险供应链入口。

### 兼容门

正式支持的平台、操作系统和 Agent 均有对应契约测试及真实运行证据。通用规则模板不得被描述为正式适配器。

### 发布门

版本、变更日志、安装入口、升级、卸载、包白名单、校验文件和回滚路径一致且可复现。

## 测试策略

确定性能力遵循测试先行：先写能够失败的契约或回归测试，再做最小实现。Skill 行为遵循评测先行：在为样例调优前先固定真实提示、预期结果和判定标准。

评测至少覆盖：

- 应触发的直接请求。
- 未提 Skill 名称但语义应触发的请求。
- 关键词相似但不应触发的请求。
- 用户指定语言、格式、粒度或优先级的请求。
- 输入缺失、冲突、非法或超出边界的请求。
- 不应产生文件写入或不应调用外部工具的请求。
- 对 Token、耗时或输出长度敏感的请求。

新 Skill 使用无 Skill 基线；迭代现有 Skill 使用旧版本快照作为基线。评测结论同时记录断言通过率、人工质量判断、Token 和耗时，避免只优化单一指标。

## 失败恢复

失败后记录命令、退出状态、最小必要日志、环境和复现步骤，不盲目重复相同方法。Agent 定位最早失效阶段，修复后重跑受影响门，再执行最终全量门。

外部 Agent、网络或付费服务不可用时，确定性检查继续执行；相关正式支持状态保持未验证。无法证明安全或兼容的能力必须降级、隔离或移除，不能以文档声明代替验证。

## 安全与隐私

- 示例只使用保留域名、虚构用户和中性路径。
- 日志、评测输出和错误报告不得回显凭据或完整用户配置。
- 安装器不得关闭 TLS 校验、绕过签名或默认请求超出需要的权限。
- 发布前扫描工作区、Git 历史、Tag、Release 说明和发布资产。
- 第三方 Actions、脚本和依赖使用可审计、固定且最小的版本范围。
- 删除 Release 不能被视为清除 Tag 或 Git 历史中的秘密；发现真实泄露时必须按传播范围完整处置并轮换凭据。

## 最终计划要求

最终计划必须是 Agent 可直接执行的清单，而不是原则汇总。每个任务应提供：

- 适用条件和依赖输入。
- 创建、修改和测试文件的实际路径确定方法。
- 具体步骤、命令和预期结果。
- 产出的接口或文档契约。
- 通过条件和失败恢复。
- 对应质量门及提交边界。

计划必须包含简单提示型 Skill 的最短路径，也必须明确何时进入每条增强轨道。不得使用 `TBD`、`TODO`、“按需处理”但不说明判定条件，或“编写相关测试”但不给出测试范围与断言。

## 完成标准

满足以下全部条件时，设计才算落地：

1. 最新需求都能追踪到计划任务、交付物和验证证据。
2. 核心轨道全部通过，未启用的增强轨道有明确不启用理由。
3. 已启用增强轨道通过对应专项质量门。
4. 有 Skill 相对基线产生可证明的质量收益。
5. 无未处理占位符、高风险问题或未经验证的正式兼容声明。
6. 独立 Agent 只依赖计划和目标仓库即可复现开发、验证、发布准备和回滚。
7. 最终报告列出已完成能力、未启用能力、验证证据和剩余风险。
