# 暂存提交说明 Skill 精简重构设计

## 1. 背景

当前 `git-commit-assistant` 同时承担提交说明生成、外部索引事务、自动暂存、并发防护、恢复协议和提交执行等职责。运行时说明接近预算上限，测试与证据主要围绕事务实现展开，已经偏离用户真正需要的能力。

本次重构将项目收敛为一个目标：**为准备提交的暂存变更生成清晰、简洁、基于真实差异的 Git commit 说明**。暂存和提交只是用户明确授权后服务于该目标的辅助动作，不扩展为通用 Git 自动化工具。

## 2. 已确认需求

1. 提交说明采用 Conventional Commits。
2. 默认使用简体中文；用户明确指定其他语言时，主题与正文统一使用指定语言。
3. 简单修改只使用完整主题；多项改动或复杂业务变更增加最少数量的简洁处理点。
4. 默认只读取真实暂存区并展示候选说明，不修改仓库。
5. 用户明确要求暂存或提交时，允许执行 `git add`、调整暂存区和执行 `git commit`。
6. 执行提交前必须先展示完整候选说明，并等待第二次明确确认。
7. 只暂存并提交当前任务相关的文件或 hunk，无关改动保持不变。
8. 允许临时取消暂存和重组暂存区；成功、取消或失败后必须恢复无关改动原有的暂存状态。
9. 同一文件中语义独立的 hunk 必须支持分离；无法安全拆分的混合 hunk 必须停止并要求用户整理。

## 3. 目标与非目标

### 3.1 唯一目标

依据最终准备提交的确切暂存 diff，生成一条最能概括变更目的的清晰、简洁提交说明。

### 3.2 辅助能力

仅在用户明确要求时：

- 将当前任务相关文件或 hunk 加入暂存区；
- 临时调整暂存区以隔离当前任务；
- 在第二次明确确认后创建一次普通提交；
- 恢复与本次任务无关的原暂存状态。

这些动作不得改变提交说明生成这一核心职责，也不得触发未授权的 Git 操作。

### 3.3 非目标

Skill 不负责：

- push、tag、release、发布或包上传；
- amend、rebase、cherry-pick 或其他历史改写；
- 提交签名、跳过或绕过 hook；
- 修改 Git、Codex 或仓库配置；
- 通用 Git 教学、历史分析或分支管理；
- 对抗能够精确操纵进程与文件系统调用间隙的同权限恶意进程。

## 4. 总体架构

运行时仅包含：

```text
git-commit-assistant/
├── SKILL.md
└── scripts/
    └── staged-commit.mjs
```

### 4.1 `SKILL.md`

负责模型需要理解的语义判断：

- 判断请求是仅生成说明，还是明确暂存/提交；
- 从对话与 diff 确定当前任务范围；
- 识别文件和 hunk 是否属于当前任务；
- 选择语言、type、scope 和说明粒度；
- 生成并展示唯一的最佳候选说明；
- 识别第二次确认以及安全停止条件。

目标长度为不超过约 900 个保守 prompt token，删除事务实现细节、威胁模型论证和重复规则。

### 4.2 `scripts/staged-commit.mjs`

只负责确定性的 Git 状态处理，不解释业务语义，不生成提交文案：

- 读取可供 Agent 选择的文件与 hunk 清单；
- 保存原 HEAD、索引和恢复所需资料；
- 按 Agent 给出的选择整理真实暂存区；
- 生成与 HEAD、暂存树和完整消息绑定的确认标识；
- 取消时恢复原索引；
- 确认有效时执行一次普通 `git commit`；
- 成功后恢复原先无关改动的暂存状态；
- 失败或无法自动恢复时保留可识别的恢复资料并安全停止。

脚本使用 Node.js 标准库和 Git，不增加运行时依赖。接口保持少量命令和单行 JSON 输入输出，避免把内部补丁、敏感值或冗长 Git 输出展示给用户。

## 5. 工作流

### 5.1 仅生成说明

1. 确认当前目录属于 Git 工作树。
2. 读取适用的仓库规则、Git 特殊状态、暂存路径、`git diff --cached`、统计信息和必要的近期提交主题。
3. 暂存区为空、处于不适合普通提交的 Git 状态或发现疑似敏感内容时，给出简洁停止原因。
4. 根据确切暂存 diff 生成候选说明。
5. 只展示候选说明和必要的证据限制，不执行暂存或提交动作。

未暂存和未跟踪内容不能用于填补空暂存区，也不能被暗中纳入候选说明。

### 5.2 明确暂存或提交

1. 根据用户请求和当前对话确定当前任务边界。
2. 读取已暂存、未暂存和与任务相关的未跟踪内容，形成文件/hunk 清单。
3. 选择当前任务单元：
   - 文件内语义独立的 hunk 可以分别选择；
   - 未跟踪文件、二进制变更、重命名和模式变更作为原子单元；
   - 一个原子 hunk 混合当前任务与无关修改时停止。
4. 脚本保存原索引并将真实暂存区整理为仅包含当前任务。
5. Agent 必须重新读取整理后的确切 staged diff，并据此生成候选说明。
6. 展示纳入提交的路径、hunk 数量、完整候选说明和短确认标识。
7. 等待新的明确确认：`确认提交 <标识>`。
8. 取消、拒绝、沉默、歧义回复或消息修改均不构成确认；脚本恢复原索引。
9. 确认前重新验证 HEAD、暂存树和消息。任一绑定变化都会使旧确认失效，并恢复或重新检查。
10. 确认有效时执行一次保留 hook 的普通提交。
11. 成功后恢复原有无关暂存内容；失败时恢复提交前索引。无法可靠恢复时保留恢复资料，不覆盖工作区内容。

## 6. 提交说明规范

基本格式：

```text
type(scope): 主题
```

- `type` 从 staged diff 的主要意图选择，支持 `feat`、`fix`、`refactor`、`docs`、`test`、`chore`、`build`、`ci`、`perf` 和 `style`。
- `scope` 仅在模块或业务边界有可靠证据时使用；无法确认时省略。
- 只有 staged diff 明确体现破坏性变更时才使用 `!` 或 `BREAKING CHANGE`。
- 主题概括“为什么进行这次提交或它完成了什么”，通常不超过 72 个字符，不加句号。
- 当主题已经完整覆盖一两个简单改动时，不添加正文。
- 多项实质改动或复杂业务变更使用一个空行和最少数量的 `- ` 处理点。
- 处理点按业务或实现语义合并，不逐文件罗列，不重复主题，不描述 diff 无法证明的原因、收益或结果。
- 默认只输出一个最佳候选；用户明确要求时才给出备选。

示例：

```text
feat(remittance): 添加打款账户启用状态管理

- 新建账户时默认启用，并通过专用接口变更启停状态
- 查询和转账时校验账户状态，排除已停用账户
- 限制通用编辑入口绕过启停规则
```

## 7. 状态绑定与错误处理

第二次确认只绑定以下最小状态：

- 当前 HEAD；
- 当前任务的 staged tree；
- 选中的文件/hunk 集合；
- 完整候选消息。

短确认标识由上述状态摘要产生，用于避免“确认”误用于已经变化的候选。它不是权限令牌，不需要旧实现中的所有权协议或父进程认证。

以下情况安全停止：

- 暂存区为空且用户没有授权暂存；
- 当前任务范围不明确；
- 混合 hunk 无法安全拆分；
- 合并、变基、cherry-pick 或 revert 等特殊 Git 状态；
- 疑似包含密钥、令牌或其他敏感材料；
- 候选展示后 HEAD、索引、选择或消息发生变化；
- hook 拒绝提交；
- 恢复校验失败或检测到外部并发修改。

错误输出只包含停止原因、仓库是否已恢复以及一个安全的下一步，不回显敏感内容、内部补丁或原始 hook 输出。

删除以下已经失效且可由 Git 历史恢复的内容：

## 9. 测试与评测策略

确定性行为遵循 TDD：先添加会因目标行为缺失而失败的测试，再实现最小功能。

### 9.1 脚本测试

- 只读检查不改变 HEAD、索引、工作区或对象库；
- 选择单文件和多文件任务改动；
- 分离同一文件中的独立 hunk；
- 混合原子 hunk 拒绝准备；
- 保留并恢复无关 staged 内容；
- 取消、无效确认和 hook 失败后恢复原状态；
- HEAD、staged tree、选择或消息变化使确认失效；
- 成功提交只包含所选任务内容；
- 不产生 push、tag、amend、签名、hook 绕过或配置写入。

### 9.2 Skill 行为评测

使用隔离 Git 仓库验证：

- 默认中文与显式语言覆盖；
- 简单主题和复杂处理点；
- 无 scope 证据时省略 scope；
- 仅生成说明请求保持只读；
- 明确提交请求必须二次确认；
- 当前任务选择、独立 hunk 拆分和混合 hunk 停止；
- 相邻 Git 教学、历史查询、push 或 amend 请求不扩展 Skill 权限。

静态文本断言只能验证结构，不能替代真实 Agent 行为结论。

## 10. 验收标准

1. Skill 的所有说明均围绕唯一目标，无旧事务威胁模型和脚手架维护能力残留。
2. 默认中文，显式语言覆盖有效。
3. 候选说明只依据最终确切 staged diff，不根据文件名或对话虚构内容。
4. 简单提交无冗余正文，复杂提交具有最少且清晰的处理点。
5. 未明确授权时不修改暂存区；未二次确认时不执行提交。
6. 当前任务与无关改动能够按独立 hunk 隔离，混合 hunk 安全停止。
7. 成功、取消和失败路径均不丢失用户改动，并恢复应保留的无关 staged 状态。
8. 无新增运行时依赖，`SKILL.md` 不超过约 900 个保守 prompt token。
9. `npm run check`、`npm run gate:delivery`、正向/负向/边界评测和包白名单审计通过。
10. README 使用中文且准确描述最终行为；全局安装副本与仓库运行时一致。

## 11. 迁移与交付

1. 更新 Skill Brief 的需求版本、冲突记录、能力轨道和验收标准。
2. 以测试先行方式替换旧脚本和工作流。
3. 删除已失效的通用脚手架与事务资产。
4. 更新 README、决策记录、交付报告、评测和包白名单。
5. 运行聚焦测试、完整 `npm run check`、审计和 `npm run gate:delivery`。
6. 审查完整 diff、未跟踪文件、敏感信息和中文代码注释。
7. 验证通过后，将 `SKILL.md` 和 `scripts/staged-commit.mjs` 同步到全局安装目录；保留已有可恢复备份，不复制开发文件。

本设计取代旧的事务式自动暂存设计作为当前实现依据。旧提交与历史文档仅作为 Git 历史记录，不再构成产品行为承诺。
